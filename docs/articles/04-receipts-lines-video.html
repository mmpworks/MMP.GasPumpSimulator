Receipts, lines, and a video player

Three more asks for the detergent example:

  • The bank wants the charges itemized.
  • The driver wants to print an itemized receipt for a short while after hanging up the nozzle.
  • A video should play when fueling starts, from a player that lives apart from everything else.

Two seams carry all three. Below is the code that proves them. The features that sit on top are sketches.

Hypothetical code in green-edged blocks is a sketch. DispenserStation mark real code.

1. The three asks

  1. The bank gets an itemized breakdown of the charges along with the completion. It uses that for:
    • record-keeping,
    • the dispute desk.
  2. The driver can print an itemized receipt at the end. The offer lasts only a little while after the nozzle goes back in the boot.
  3. A video plays when pumping starts. The player runs apart from everything else. If it crashes, the sale, the pump, and the money never notice.

The first two are one fact with two readers. Think of a store receipt: the shop keeps a copy and the customer takes a copy, and both copies match.

The third is a new kind of part. It is a listener that reads the station's telemetry and may never write back.

Each ask needed a seam the code didn't have this morning. Both seams landed in commit 16cdbc4. The suite is 275 of 275 at ebbf956.

2. Charge lines, from the pump to the bank

BothThe pump itemizes the money where it prices it. The breakdown then rides beside the total through every hop the total already made. Nothing recomputes it. The receipt and the settlement read the same list.

// Description is for the receipt. The bank receives the list with the completion and the
// driver can print it, so the two always agree with each other and with the total.
public sealed record ChargeLine(string Code, string Description, Money Amount)
{
    public const string Fuel = "FUEL";
    public static Money Total(IEnumerable<ChargeLine> lines) { /* sum */ }
}

public interface IPriceSchedule
{
    Money CentsFor(Grade grade, Volume volume);
    Volume MaxVolumeFor(Grade grade, Money money);
    string Display(Grade grade);

    // The same money as CentsFor, broken into the lines a receipt and a settlement carry.
    // The board answers with one fuel line; a schedule that wraps it adds its own.
    IReadOnlyList<ChargeLine> Lines(Grade grade, Volume volume) =>
        [new ChargeLine(ChargeLine.Fuel, $"{grade} {volume} at {Display(grade)}/gal", CentsFor(grade, volume))];

Along the way, the sale machine keeps the last breakdown the pump sent. An old pump may send none. Then the machine falls back to one fuel line, so an old dispenser process still settles cleanly.

[Theory] [MemberData(nameof(SimHarness.Strategies), MemberType = typeof(SimHarness))]
public void The_bank_receives_the_charges_itemized_and_the_receipt_reads_the_same_lines(string strategy)
{
    using var h = new SimHarness(strategy, ThirtyDollarHold);
    h.Sim.PresentCard("Good");
    h.AdvanceUntilState(SaleState.ReadyToPump, TimeSpan.FromSeconds(5));
    Assert.Empty(h.State.Charges);   // nothing to itemize before fuel moves

    h.Sim.StartFueling();
    h.AdvanceUntil(() => h.State.State is SaleState.Completing or SaleState.Idle, TimeSpan.FromMinutes(3));
    h.AdvanceUntilState(SaleState.Idle, TimeSpan.FromSeconds(5));

    // What the driver can print: the same lines the pump priced, summing to the money on the screen.
    var receipt = h.State.Charges;
    Assert.Single(receipt);
    Assert.Equal(ChargeLine.Fuel, receipt[0].Code);
    Assert.Equal(h.State.Money, ChargeLine.Total(receipt));

    // What the bank kept: the same lines, under the same sale id, summing to the settled amount.
    var settlement = Assert.Single(h.Sim.Issuer.Settlements);
    Assert.Equal(h.State.SaleId, settlement.SaleId);
    Assert.Equal(Money.FromDollars(30), settlement.Final);
    Assert.Equal(receipt, settlement.Lines);
}

3. The receipt and its time limit

StationThe receipt is a pure function of the sale snapshot. Same snapshot in, same text out. The snapshot already carries:

  • the charges,
  • the tender,
  • where the money is,
  • when the screen will clear.

The time limit on the offer is a timer the sale already runs.

Here is the clock, step by step:

  1. The nozzle hangs up.
  2. The sale goes to Completing.
  3. The bank answers, and the sale goes to Idle.
  4. The terminal screen holds for the notice timeout (30 seconds by default). Then it clears for the next driver.

If the bank still owes an answer, the screen holds longer, on purpose. SaleSnapshot.DeadlineAt is the moment the screen clears, and the receipt offer ends with it. A longer window would be one field on SaleTimeouts.

// GasPump.Core/Receipt.cs (sketch). Pure: snapshot in, text out.
public sealed record Receipt(string SaleId, string PumpId, DateTimeOffset At, IReadOnlyList<ChargeLine> Lines, Money Total, Tender Tender, HoldStatus Hold, Money ChangeDue)
{
    public static Receipt? From(SaleSnapshot s, string pumpId, DateTimeOffset now)
    {
        // Offer window: the sale has ended, fuel moved, and the screen has not cleared yet.
        var ended = s.State is SaleState.Completing or SaleState.StoreAndForward or SaleState.Faulted || (s.State == SaleState.Idle && s.Charges.Count > 0);
        if (!ended || s.Charges.Count == 0) return null;
        if (s.DeadlineAt is { } deadline && now > deadline) return null;      // the offer has expired with the screen
        return new(s.SaleId, pumpId, now, s.Charges, ChargeLine.Total(s.Charges), s.Tender, s.Hold, s.ChangeDue);
    }

    public string Print() { /* fixed-width lines, one per charge, total, hold status in words */ }
}

// GasPump.Host/Program.cs (sketch): one endpoint, one state code when the offer is over.
app.MapGet("/api/receipt", () =>
    Receipt.From(Sim().Snapshot(), Sim().Options.PumpId, clock.GetUtcNow()) is { } r
        ? Results.Text(r.Print(), "text/plain")
        : Results.StatusCode(410));   // Gone: the screen cleared, the offer with it

// Ledger, so the audit shows the receipt was issued:
Ledger.Append("receipt.printed", $"{r.SaleId} {r.Total} {r.Lines.Count} lines");

4. Capabilities: telemetry on its own worker

StationA video player is a new kind of part. It reads what the station knows and must never be able to change it. Think of a customer watching the shop through a window: they can look, but they can't reach in. So the seam is a listener with:

  • no return value,
  • no handle,
  • its own worker,
  • its own bounded mailbox (a slip tray with a fixed size).

The host enforces three isolation rules:

  1. A full mailbox drops the message and counts it, so a slow capability never blocks the sale worker.
  2. A capability that throws is switched off for the rest of the run, and the log says so.
  3. A capability never receives a handle to anything it could change.

src/GasPump.Dispatch/Capabilities.cs · Simulation.cs

// A listener on the station's telemetry. A capability reads; it never writes to the sale,
// the pump, or the bank. It has no return value and no way to post a message back.
public interface IStationCapability
{
    string Name { get; }
    void OnSaleEvent(SaleEvent e);                 // one sale event, after the sale machine applied it
    void OnPumpView(DispenserView v) { }           // one view of the pump, as the dispenser sent it
}

// Isolation, in three rules. A full mailbox drops the message and counts it, so a slow
// capability never blocks the sale worker. A capability that throws is switched off for
// the rest of the run and the log says so. A capability never receives a handle to
// anything it could change.
public sealed class CapabilityHost(IDispatchStrategy dispatch, IEventLog log)
{
    public void Register(IStationCapability capability)
    {
        var slot = new Slot(capability, dispatch.CreateMailbox<object>($"capability:{capability.Name}", MailboxCapacity));
        slot.Worker = dispatch.StartWorker($"capability:{capability.Name}", slot.Inbox, m => Deliver(slot, m));
        lock (_gate) _slots.Add(slot);
    }

    private void Fan(object message)
    {
        foreach (var slot in Snapshot())
        {
            if (slot.Disabled) continue;
            if (slot.Inbox.TryPost(message)) continue;
            // The sale worker never waits on a capability, because a driver is standing at the hose.
            if (Interlocked.Increment(ref slot.Dropped) == 1) log.Warn("capability", "{Name} mailbox full, dropping telemetry", ("Name", slot.Capability.Name));
        }
    }

    private void Deliver(Slot slot, object message)
    {
        if (slot.Disabled) return;
        try
        {
            switch (message)
            {
                case SaleEvent e: slot.Capability.OnSaleEvent(e); break;
                case DispenserView v: slot.Capability.OnPumpView(v); break;
            }
        }
        catch (Exception ex)
        {
            slot.Disabled = true;
            log.Error("capability", "{Name} threw {Type}: {Message}; switched off for this run", /* ... */);
        }
    }
}

// Simulation: two lines feed it.
_link.ViewChanged += v => Capabilities.Publish(v);

public void A_capability_sees_the_telemetry_on_its_own_worker_and_one_that_throws_cannot_touch_the_sale(string strategy)
{

    var recorder = new Recorder();
    h.Sim.Capabilities.Register(recorder);
    h.Sim.Capabilities.Register(new Bomb());

    // ... a full sale ...

    // The sale finished as if nothing were attached.
    Assert.Equal(3000, h.State.Money.Cents);
    Assert.Equal(HoldStatus.Settled, h.State.Hold);
    Assert.Equal(0, h.Sim.Ledger.Verify());

    Assert.Equal(1, recorder.FlowStarts);

}

The test runs under all three dispatch strategies. The capability worker is one of these, depending on the row:

  • a thread,
  • a task,
  • an AsyncProxy state machine.

The isolation holds in each.

5. The video player, as a sketch

HypotheticalTake "apart from everything else" literally: the player is another process. The capability has two jobs:

  • start the player on FlowStarted,
  • stop it when the sale ends.

If the player hangs or dies, the capability notices on the next event. Nothing else does.

// GasPump.Host/PumpStartVideo.cs (sketch)
public sealed class PumpStartVideo(string playerPath, string clipPath, IEventLog log) : IStationCapability
{
    public string Name => "video";
    private Process? _player;

    public void OnSaleEvent(SaleEvent e)
    {
        switch (e)
        {
            case SaleEvent.FlowStarted:
                Stop();
                // The player runs in its own process and window, with no handle back into ours. A crash there stays there.
                _player = Process.Start(new ProcessStartInfo(playerPath, $"-fs -autoexit \"{clipPath}\"") { UseShellExecute = false });
                log.Write("video", "playing {Clip} for {SaleId}", ("Clip", clipPath), ("SaleId", e.SaleId));
                break;
            case SaleEvent.NozzleHung or SaleEvent.CeilingReached or SaleEvent.Fault or SaleEvent.Cancel:
                Stop();
                break;
        }
    }

    private void Stop()
    {
        try { if (_player is { HasExited: false }) _player.Kill(); } catch (Exception) { /* the player is a separate process; a failed kill is ignored */ }
        _player = null;
    }
}

// GasPump.Host/Program.cs (sketch): registration is one line, from configuration.
if (Environment.GetEnvironmentVariable("GASPUMP_VIDEO_PLAYER") is { } player)
    host.Current.Capabilities.Register(new PumpStartVideo(player, clipPath, log));

In the Electron app the same capability could open a second BrowserWindow on the forecourt display instead. It would send that window one message. Either way the sale worker never knows there is a screen.

Why a capability instead of a WebSocket client. The host already streams every event on /ws, so an outside program could watch that. A capability is for a part that ships with the station. It has to start and stop with the station. Both routes read the same telemetry, and neither can write.

7. What the bank now sees

StationUntil today the completion was one number. Now it's that number plus the list that explains it. The number itself didn't change, so these all run as before:

  • the hold,
  • the partial-approval rule,
  • the clamp,
  • the reversal path,
  • the recovery table.

What changed is what the bank can answer when a driver calls.

StepBeforeNow
CompletionComplete(saleId, $30.00)Complete(saleId, $30.00, [FUEL $28.50, ADDITIVE $1.50]). The sum is checked at the pump on every tick and by the tests at the bank.
Dispute"You were charged $30.00 at pump 7.""You were charged $28.50 for 8.146 gal of Regular and $1.50 for the additive you selected at 14:19:03." The ledger has the selection and every valve switch; the custody chain seals them.
Crash before the bank answeredThe journal held the total; recovery resent it.The journal holds the lines; recovery resends the same lines. The receipt the driver printed and the settlement the bank keeps still match.
CashChange at the till from the total.Same. The till owes change on the total; the lines are for the receipt.
Taxes and reportingFuel revenue was reconstructed from the ledger.Fuel and additive are separate lines with stable codes. The back office sums by code. No reconstruction.
