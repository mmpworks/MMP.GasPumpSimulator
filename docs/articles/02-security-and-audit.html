1. Assets and attackers

Two trust boundaries, two jobs. The card reader guards the card, and the pump controller guards the fuel. The simulator builds the pump controller. It only names the card reader.

FuelVolume leaving the hose that nobody paid for.
The holdMoney on a driver's card that should be released, or settled to the real amount.
The recordA ledger and a totalizer that let the books be checked against the meter.
  • Upstream owned. The attacker has taken over one of these:
    • the payment host,
    • the site controller,
    • the wire between them.
    The attacker can send any message to the pump, including a correctly signed one.
  • On the wire. The attacker can capture and replay messages between the host and the pump.
  • At the pump. The attacker can feed the meter input, as a spoofed pulser would.
  • At the host. The network to the processor is in one of three bad states:
    • down,
    • slow,
    • going up and down.

2. Three ceilings, in order

BothA sale's ceiling passes three gates, in this order. Each gate can only lower it.

  1. Site ceiling. SiteLimits holds it, behind a PIN. Credit is $75, debit is $50, and cash is the cash amount. The admin panel can move this gate anywhere.
  2. The bank's yes. The approved amount, which may be partial. A signed token then carries it to the pump.
  3. Hard limit. HardLimits inside the pump: $500, 50 gallons, 10 minutes. It is set at construction and never from a message. This gate stays put.
// The numbers the pump will never exceed, whatever anyone upstream says.
// Set once at construction, from the pump's own configuration, never from a message.
public sealed record HardLimits(
    Money MaxMoneyPerSale,
    Volume MaxVolumePerSale,
    TimeSpan MaxSaleDuration,
    FlowRate MaxFlow,
    long MaxPulsesPerTick)
{
    public static HardLimits Default => new(
        MaxMoneyPerSale: Money.FromDollars(500),
        MaxVolumePerSale: Volume.FromGallons(50),
        MaxSaleDuration: TimeSpan.FromMinutes(10),
        MaxFlow: FlowRate.GallonsPerMinute(12),
        // A tick is 100 ms. 12 gal/min is 20 mGal per tick. Anything far above that is a spoofed pulser.
        MaxPulsesPerTick: 60);
}

3. The token and the order of checks

BothThe payment side hands the pump one string: this sale, this pump, this much, this long, once. Think of a permission slip with a wax seal. Field order is the contract. Change it and every pump rejects every token.

src/GasPump.Payment/AuthorizationToken.cs · src/GasPump.Security/PumpAuthority.cs

public sealed record AuthorizationToken(
    string SaleId, string PumpId,
    long CeilingCents, long MaxMilliGallons,
    long IssuedAtUnixMs, long ExpiresAtUnixMs,
    string Nonce, string Signature)
{
    // The bytes that are signed.
    public string Payload() => $"{SaleId}|{PumpId}|{CeilingCents}|{MaxMilliGallons}|{IssuedAtUnixMs}|{ExpiresAtUnixMs}|{Nonce}";
}

// HMAC-SHA256 over the payload. The verifier in GasPump.Security holds the same key.
public static string Sign(byte[] key, string payload) =>
    Convert.ToHexString(HMACSHA256.HashData(key, Encoding.UTF8.GetBytes(payload)));

The verifier runs four checks in a fixed order. A token that cannot be parsed is refused before check 1.

  1. Signature. Is the seal good? The comparison runs in constant time.
  2. Pump id. Is the token for this pump?
  3. Time window. Is now between issue time and expiry, give or take the clock-skew allowance?
  4. Nonce. Is this number, used once, new to the nonce store?

A forged token fails check 1 and never reaches the nonce store. So an attacker can't burn nonces by spamming junk.

public (VerifiedAuthorization? Auth, VerifyFailure Failure) Verify(string wire, DateTimeOffset now)
{
    AuthorizationToken token;
    try { token = AuthorizationToken.Parse(wire); }
    catch (Exception) { return (null, VerifyFailure.BadFormat); }

    var expected = HmacAuthorizationSigner.Sign(key, token.Payload());
    if (!CryptographicOperations.FixedTimeEquals(Encoding.ASCII.GetBytes(expected), Encoding.ASCII.GetBytes(token.Signature)))
        return (null, VerifyFailure.BadSignature);           // 1. signature, in constant time

    if (!string.Equals(token.PumpId, pumpId, StringComparison.Ordinal))
        return (null, VerifyFailure.WrongPump);              // 2. this pump

    var issued  = DateTimeOffset.FromUnixTimeMilliseconds(token.IssuedAtUnixMs);
    var expires = DateTimeOffset.FromUnixTimeMilliseconds(token.ExpiresAtUnixMs);
    if (now < issued - clockSkew)  return (null, VerifyFailure.NotYetValid);   // 3. time window
    if (now > expires + clockSkew) return (null, VerifyFailure.Expired);

    if (!nonces.TryConsume(token.Nonce)) return (null, VerifyFailure.Replayed);  // 4. once

    return (new VerifiedAuthorization(token.SaleId, token.Ceiling, token.MaxVolume, expires), VerifyFailure.None);
}

4. The message that does not exist

DispenserThe strongest control is a message that doesn't exist. The only way to arm the pump is a token. There is no SetCeiling, no SetLimit, no OpenValve. Over the socket the dispenser accepts the same records it accepted in-process. Arm still goes through the authority and the nonce store. Stop is the one frame that needs no token, and all it can do is close the valve.

5. Replay across a reboot

DispenserA nonce store in memory forgets everything at power off, so a captured token would replay after a reboot. Two controls close that door.

src/GasPump.Security/PumpAuthority.cs (NonceStore) · src/GasPump.Dispatch/DispenserServer.cs (CustodyKeyFile)

First, the dispenser saves every nonce it burned in its state file and restores them before the first message.

public sealed class NonceStore
{
    private readonly Lock _gate = new();
    private readonly HashSet<string> _seen = new(StringComparer.Ordinal);

    public bool TryConsume(string nonce) { lock (_gate) return _seen.Add(nonce); }

    // For the journal. A restart must remember every nonce it burned, or a token replays across the reboot.
    public IReadOnlyList<string> Export() { lock (_gate) return _seen.ToArray(); }
    public void Import(IEnumerable<string> nonces) { lock (_gate) foreach (var n in nonces) _seen.Add(n); }
}

Second, the token key comes from the site's custody key. HKDF (a standard key-derivation function) makes it under a fixed label. So both processes compute the same key after any restart. A fresh random key per boot would be simpler. But every queued token would then be worthless, and every old token a mystery.

public static class CustodyKeyFile
{
    public const string TokenKeyLabel = "gaspump.token-key.v1";

    // GASPUMP_CUSTODY_IKM_HEX wins; else custody.ikm in the directory; else a new random key written there.
    public static byte[] Load(string directory) { /* ... */ }

    public static byte[] TokenKey(byte[] ikm) =>
        HKDF.DeriveKey(HashAlgorithmName.SHA256, ikm, 32, info: Encoding.UTF8.GetBytes(TokenKeyLabel));
}

The totalizer is the sealed counter on the side of a real pump. It only goes up. There is no Reset method, on purpose. It can be loaded from the journal once, before the first sale, while it still reads zero.

public sealed class Totalizer
{
    private long _milliGallons;
    public Volume Total => new(Interlocked.Read(ref _milliGallons));

    public void Add(Volume delivered)
    {
        if (delivered.MilliGallons < 0) throw new ArgumentOutOfRangeException(nameof(delivered), "a totalizer never goes down");
        Interlocked.Add(ref _milliGallons, delivered.MilliGallons);
    }

    public void Restore(Volume journaled)
    {
        if (Interlocked.CompareExchange(ref _milliGallons, journaled.MilliGallons, 0) != 0)
            throw new InvalidOperationException("a totalizer is restored once, before the first sale");
    }
}

8. Audit: three records, one code

BothEvery fault, every arm, and every admin attempt lands in three places:

  • the debug log on Herald.OSS,
  • the hash-chained ledger,
  • the TesseraSeal custody chain.

One diagnostic code goes in all three. So whoever reads any one of them can tell a dead pulser from an empty tank without reading the prose.

src/GasPump.Core/Diagnostics.cs · src/GasPump.Security/EventLedger.cs · src/GasPump.Custody

The ledger is append-only and hash-chained. Every entry carries the hash (a fingerprint) of the one before it. Edit entry 7 and entries 8 onward no longer match. Verify walks the whole chain. It returns the first broken sequence number, or 0 when the chain is intact.

public sealed record LedgerEntry(long Seq, DateTimeOffset At, string Kind, string Detail, string PrevHash, string Hash)
{
    public static string Compute(long seq, DateTimeOffset at, string kind, string detail, string prevHash)
    {
        var bytes = Encoding.UTF8.GetBytes($"{seq}|{at.ToUnixTimeMilliseconds()}|{kind}|{detail}|{prevHash}");
        return Convert.ToHexString(SHA256.HashData(bytes));
    }
}

public static long Verify(IReadOnlyList<LedgerEntry> entries)
{
    var prev = Genesis;
    for (int i = 0; i < entries.Count; i++)
    {
        var e = entries[i];
        if (e.Seq != i + 1) return e.Seq;
        if (e.PrevHash != prev) return e.Seq;
        if (LedgerEntry.Compute(e.Seq, e.At, e.Kind, e.Detail, e.PrevHash) != e.Hash) return e.Seq;
        prev = e.Hash;
    }
    return 0;
}

9. Custody in two places

BothA chain kept only on the dispenser dies with the dispenser. So the dispenser publishes every custody line, byte for byte, as it lands. The station appends the same bytes to its own file, one file per dispenser run. It checks the copy with the same key. The line a subscriber receives is the line the verifier will read.

src/GasPump.Dispatch/CustodyStream.cs · src/GasPump.Host/StationServer.cs

// The station's copy of the dispenser's chain.
private void OnLine(string runId, string line)
{
    lock (_gate)
    {
        if (runId != RunId)
        {
            RunId = runId;
            CopyPath = Path.Combine(_directory, $"station-copy-{runId}.ndjson");
            LinesReceived = File.Exists(CopyPath) ? File.ReadLines(CopyPath).Count() : 0;
        }
        File.AppendAllText(CopyPath!, line + "\n");
        LinesReceived++;
    }
}

// Run TesseraSeal's verifier over the station's copy.
public (bool Ok, long? FailureAtSeq, string? Reason, int Lines) VerifyCopy()
{
    lock (_gate)
    {
        if (CopyPath is null || !File.Exists(CopyPath)) return (false, null, "no station copy yet", 0);
        var ok = ImmutableAuditFileSink.VerifyChain(CopyPath, _ikm, out var seq, out var reason);
        return (ok, seq, reason, File.ReadLines(CopyPath).Count());
    }
}

The custody chain is TesseraSeal primitive 1: an HMAC-SHA-256 chain under an HKDF session key. A changed byte fails that entry's MAC (message authentication code). A cut final newline fails the whole file. Each run is its own chain, and both sides can verify it. The host exposes /api/station/custody/verify and streams the lines on /ws/custody for any outside listener.

Attacks 31, 36Edit the custody file after the fact, or take the evidence with a dead dispenser. The edit fails at the edited entry. The station holds the copy.

10. Recovery is part of the audit

StationA record that claims more than it knows is a bad record. So the restart decision states what it cannot count. After a crash, fuel may have moved for up to one snapshot period, at the last flow rate. After an E-stop that number is zero, because the E-stop wrote its own final snapshot on the way down.

// An E-stop writes its own final snapshot on the way down, so nothing flowed after it. A crash writes none.
var estop = snapshot.StopReason == "ESTOP";
var unrecorded = estop ? Volume.Zero : flow.Over(snapshotPeriod);

case SaleState.Fueling when volume > Volume.Zero:
    return new(RecoveryKind.ClosedOut, /* ... */ unrecorded, age,
        estop
            ? $"{how} while fueling; closed for {volume} at {money}; the E-stop cut power with the valve open, nothing flowed after the final snapshot"
            : $"{how} while fueling; closed for {volume} at {money}; delivery likely under-recorded by up to {unrecorded}");

The outcome goes in the ledger and the custody chain under recovery. An auditor reads the gap as a stated bound.

11. Where CAP comes in

BothThe CAP theorem says a networked system can't have all three of these at once when the network breaks:

CConsistency. Every reader sees the same, latest truth.
AAvailability. Every request gets an answer, even while the link is down.
PPartition tolerance. The system keeps working when the link is cut.

Partitions happen, so P is a given. The question at each wire is what to do when the link is down: answer anyway (A), or refuse until we know (C)? The simulator has two wires. It answers differently at each wire, and differently at each step of the sale.

Wire 1, authorization: consistency wins

No answer from the bank means no fuel. The station waits 30 seconds and declines. A late approval that arrives after that gets reversed, and the pump stays unarmed. What's at risk here is fuel nobody paid for, so the system refuses to guess.

// From approval to the first lift, with the card read at the pump, authorization waits 30 s.
public sealed record SaleTimeouts(TimeSpan Authorization, TimeSpan NozzleLift, TimeSpan NozzleLiftAtStation, TimeSpan Notice, TimeSpan MaxFueling);

case SaleEvent.Approved late when State != SaleState.Authorizing:
    // Late approval after we gave up. Give the hold back.
    Hold = HoldStatus.Held;
    commands.Add(new SaleCommand.Reverse(SaleId));
    return true;

Wire 1, settlement: availability wins, with a log

Fuel has moved, and the driver shouldn't have to stand at the pump until the bank wakes up. So three things happen:

  1. The completion or reversal goes into the compensation log (the undo-and-retry list) on disk.
  2. The driver is told the hold is pending.
  3. The queue drains when any call succeeds.

Two facts make this eventual consistency (the books catch up later) safe:

  • the intent is on disk before the wire is tried,
  • the bank treats a repeat as the same message, so doing it twice changes nothing.
// Intent first, then one send path for everything owed, oldest first.
var advice = new PendingAdvice(saleId, PendingKind.Completion, final);
Intend(advice);
var sent = await DrainPendingAsync(ct);
return sent.Contains(advice)
    ? new CompletionResult(true, false, $"completion {final} sent")
    : new CompletionResult(false, true, $"host {LastOutcome}, completion {final} queued");

Wire 2, mid-sale: bounded availability on the island

The dispenser is an island on purpose. When the station vanishes with the valve open, the dispenser keeps pouring. It pours only under the token it already holds and the hard limits it owns:

  • the ceiling,
  • the volume,
  • the ten-minute clock.

The token is a lease, like a rental that ends at a set time. Its expiry and ceiling cap how far the island can drift from the station's truth. Availability stretches only as far as a signed and clamped number allows.

The station makes the opposite choice. A pump it can't reach is a pump it must not pretend to drive. Posts are dropped and counted while the link is down. The sale then does three things:

  1. It faults with LINK.DISPENSER.LOST.
  2. It settles for the fuel recorded so far.
  3. It sends the driver to the attendant.
private void OnDispenserConnection(bool up)
{
    if (_frozen) return;   // the station cut this link itself; see EmergencyStop
    var code = DiagnosticCodes.LinkDispenserLost;
    if (up)
    {
        Ledger.Append("link.up", $"dispenser {_link.RemoteRunId} pid {_link.RemotePid}");
        _link.Post(new PumpMessage.Stop("station connected"), CurrentSaleId);   // a valve left open shuts first
        return;
    }
    var s = Snapshot();
    Ledger.Append("link.down", code.Format($"sale {s.SaleId} {s.State} {s.Volume} {s.Money}"));
    if (s.State is SaleState.Authorizing or SaleState.ReadyToPump or SaleState.Fueling)
        _saleBox.Post(new SaleEvent.Fault(s.SaleId, "dispenser link lost", code.Code));
}

Wire 2, reconnect: the records converge

The first frame a new station sends is Stop. The dispenser answers by sending back, in this order:

  1. its whole ledger,
  2. the tail of its log,
  3. the custody chain from the header.

The station then drops the overlap:

  • It de-duplicates the ledger by run and sequence.
  • It skips the custody lines its copy already holds, by count. This works because the chain is append-only and the prefix matches.

After the replay the two copies hold the same bytes. The hash chain is the proof.

// What this run already wrote before the station arrived: the ledger in full,
// the last stretch of the log, then the whole chain so far, then live.

if (_stream is not null)
{
    _custodyHandler = line => Send(new LinkFrame(LinkFrame.TagCustody, Line: line));

What never crosses a wire

Some state is kept on one side so no agreement is ever needed.

  • Dispenser only: the nonce store and the hard limits.
  • Station only: the sale, the journal, and the compensation log.

Each of these has one writer. So there is no consensus to run (no vote between the two sides) and no split brain to heal (two copies that each think they are right). The cheapest way through CAP is to arrange things so the two sides never have to agree on the same row.

Without a partition, the trade is latency. The station journals every change to the compensation log. It streams every custody line as it lands. Each decision costs a disk write and a socket write. The simulator pays that cost, since a record written late may never get written.

12. Out of scope, on purpose

The simulator leaves out five things.

  1. Card data. There is none. A real reader encrypts the card inside a tamper-proof boundary, using a DUKPT key (a fresh key for every swipe). The terminal never sees digits. That is PCI PTS territory (the PIN Transaction Security standard).
  2. Key management. The payment host and the pump share one HMAC key, derived from the site custody key. A real site gives each device its own key. It also adds a counter, so the pump can refuse out-of-order commands.
  3. Physical attacks on the meter. The pulse check catches a pulser that reads too high. A meter that reads too low gives fuel away. Only the totalizer compared with the tank dip (a manual reading of the tank level) would show it.
  4. Denial of service. An attacker who can reach the pump mailbox can fill it with junk. Mailboxes have a size limit, so the attacker has to wait for room. The driver waits too.
  5. Merkle seal and HSM signature on the custody chain. An HSM is a hardware security module. The chain uses TesseraSeal primitive 1 only.
