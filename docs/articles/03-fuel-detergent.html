MMP.GasPumpSimulator · article 3 · 2026-11-01

Adding fuel detergent without touching the pump

A thought experiment, with real code. Say a station wants to sell a detergent additive at the hose. The driver opts in. An injector doses it in step with the fuel. The sale bills one flat fee for it. We'll walk that request through the simulator. We'll see where the design already made it a bolt-on, and the two spots that needed a fix first.

Hypothetical code in green-edged blocks is a sketch and lives nowhere in the repo. DispenserStation mark the real code.

1. The ask

The detergent shares the hose with the fuel. A sale goes like this:

  1. The driver picks the detergent before the first squeeze.
  2. Fuel runs alone for the first three seconds.
  3. A valve flips. 16 fl oz of additive goes down the hose.
  4. The valve flips back. 16 fl oz of fuel follows.
  5. The two keep taking turns until the configured amount of additive is out.

Three money rules go with it:

  • The fuel meter counts only while fuel flows.
  • The station charges one flat fee for the additive, $1.50 in this example, whatever the fuel volume.
  • The fee is owed in full once the additive has started, even if the sale faults before it finishes.

If the additive tank runs dry, the pump should refuse to sell the option. It should say why, with a code an auditor can read.

That boils down to eight requirements:

  1. A choice the driver makes at the pump, locked once fuel has moved.
  2. A three-second lead of fuel before the first additive slug.
  3. Alternating slugs: 16 oz additive, 16 oz fuel, until the configured total (in ounces) is delivered.
  4. The fuel meter and the totalizer stand still while additive moves. Only fuel is metered.
  5. Every valve switch, each way, is in the ledger and the custody chain.
  6. A flat fee on the sale. It is owed in full from the first additive slug. The sale still lands on the cent under the ceiling.
  7. An out-of-service condition with its own diagnostic code when the additive is out.
  8. A record of each dose in the ledger.

The test of the design: which classes have to change to meet those eight requirements, and which shouldn't. The money path and the security path should stay put. Six classes have no business knowing what detergent is:

  • the sale machine,
  • the payment gateway,
  • the authority,
  • the meter,
  • the totalizer,
  • the ledger.

2. What the code looked like this morning

GapTwo places would have forced an edit to a lower-level class.

Gap 1: the controller priced with a concrete record

The pump controller took Pricing, a sealed record keyed by grade. A fee changes the answer to "how much is this sale?" There were two ways in:

  • edit Pricing,
  • edit the two lines in the tick that call it.

Both sit on the money path.

// Before. PumpController's constructor.
public sealed class PumpController(
    PumpAuthority authority,
    Hydraulics hydraulics,
    Meter meter,
    Totalizer totalizer,
    EventLedger ledger,
    Pricing pricing,          // a concrete type, so nothing can wrap it to add a fee
    TaperPolicy taper,
    TimeProvider clock)

Gap 2: nothing could see a metered slice, and nothing could take the hose

The tick counted fuel into the meter and the totalizer, then priced it. Three things blocked a bolt-on part:

  • Nothing came after the totalizer, so an injector had nowhere to listen.
  • A part couldn't say "this slice is mine, shut the fuel valve and count nothing." That made alternating slugs impossible without editing the tick.
  • The out-of-service sensor list was hard-coded to three rows. The restore table in the dispenser repeated the same three by name.
// Before. The end of PumpController.Tick.
totalizer.Add(delivered);
Money = pricing.CentsFor(grade, Volume);

// Before. The three sensors are the only conditions.
private IEnumerable<DiagnosticCode> Conditions()
{
    if (hydraulics.BreakawaySeparated) yield return DiagnosticCodes.PumpHoseBreakaway;
    if (!hydraulics.SupplyAvailable)   yield return DiagnosticCodes.PumpSupplyNoFlow;
    if (meter.PulserDead)              yield return DiagnosticCodes.PumpMeterNoPulse;
}

So no, the design wasn't ready as it stood. Most of it held up. These were all open to this change:

  • messages,
  • events,
  • the ledger,
  • the diagnostics table,
  • the sale machine.

Two seams were missing, both in the class that owns the valve. The second picked up a third method once the slug mechanics showed up. We added both today, in commits 708bac5 and ebbf956, with nothing built on them yet.

Seam 2: delivery stages see every slice

// A part bolted onto the delivery path downstream of the meter: an additive
// injector, a vapor-recovery monitor, a blend ratio check. The controller hands
// every stage the slices the meter counted and asks each one whether it holds
// the pump out of service. It never knows what a stage is.
public interface IDeliveryStage
{
    string Name { get; }
    void OnArmed(string saleId);                        // per-sale counters start here
    void OnDelivered(Grade grade, Volume delivered);    // one metered slice, after the totalizer counted it

    // Ask to take the hose for this slice. True means this stage moves its own product
    // instead of fuel: the controller shuts the fuel valve, counts nothing on the fuel
    // meter or the totalizer, and calls Pour. The switch, each way, is a ledger entry.
    bool ClaimsHose(TimeSpan pouredFor) => false;
    Volume Pour(TimeSpan dt, FlowRate hoseFlow) => Volume.Zero;

    IEnumerable<DiagnosticCode> Conditions() => [];     // what holds the pump out of service
    bool TryRestoreCondition(string code) => false;     // a restart doesn't repair this condition
}

Here's the hose part of the controller after the change. It runs once per tick, ahead of the fuel path, so a claimed slice never reaches the meter.

public sealed class PumpController(

    TaperPolicy taper,

The proof: five tests

Each test uses a fake part built against the seam, the way the detergent would be built. The suite is 275 of 275 at commit ebbf956. We start with the two slug tests, since they cover the alternating mechanics.

[Fact]
public void A_stage_that_takes_the_hose_moves_its_product_unmetered_and_every_switch_is_in_the_ledger()
{
    var oz16 = new Volume(125);                                          // 16 fl oz = 0.125 gal
    var stage = new SlugDiverter(total: new Volume(250), slug: oz16);    // 32 oz in two slugs, after 3 s of fuel
    var rig = new Rig(stages: [stage]);
    rig.ArmAndPour(Money.FromDollars(30));
    var trace = rig.RunToStop();
    var last = trace[^1];

    // All of the additive went out, in two slugs, and none of it was metered or billed as fuel.
    Assert.Equal(new Volume(250), stage.Delivered);
    Assert.Equal(2, stage.Slugs);
    Assert.Equal(last.Volume, rig.Totalizer.Total);
    Assert.Equal(Pricing.Default.CentsFor(Grade.Regular, last.Volume), last.Money);
    Assert.Equal(3000, last.Money.Cents);
    Assert.True(last.CeilingReached);

    // While the stage held the hose the fuel volume stood still and the phase named the stage.
    for (int i = 1; i < trace.Count; i++)
        if (trace[i].TaperPhase == "additive") Assert.Equal(trace[i - 1].Volume, trace[i].Volume);

    // Nothing took the hose before three seconds of fuel had run.
    Assert.All(trace.Take(29), t => Assert.NotEqual("additive", t.TaperPhase));
    Assert.Equal("additive", trace[29].TaperPhase);

    // Four switches: to additive, back to fuel, to additive, back to fuel. Each one is a ledger entry.
    var switches = rig.Ledger.Snapshot().Where(e => e.Kind == "hose.switch").ToList();
    Assert.Equal(4, switches.Count);
    Assert.Contains("fuel -> additive", switches[0].Detail);
    Assert.Contains("additive -> fuel", switches[1].Detail);
    Assert.Equal(0, rig.Ledger.Verify());
}

[Fact]
public void A_wrapped_price_schedule_changes_the_money_and_the_sale_still_lands_under_the_ceiling()
{
    // A $1.50 detergent fee on top of the board, once per sale.
    var fee = Money.FromDollars(1.50m);
    var rig = new Rig(prices: new FlatFee(Pricing.Default, fee));
    rig.ArmAndPour(Money.FromDollars(30));
    var trace = rig.RunToStop();
    var last = trace[^1];

    Assert.All(trace, t => Assert.True(t.Money.Cents <= 3000, $"{t.Money} over ceiling"));
    Assert.InRange(last.Money.Cents, 2999, 3000);
    Assert.True(last.CeilingReached);
    // The fee was billed: the same volume on the plain board costs the fee less.
    Assert.Equal(Pricing.Default.CentsFor(Grade.Regular, last.Volume) + fee, last.Money);
    // And the fuel that fits under $30 is the fuel that fits under $28.50 on the board.
    Assert.Equal(Pricing.Default.MaxVolumeFor(Grade.Regular, Money.FromDollars(28.50m)), last.Volume);
    Assert.Equal(0, rig.Ledger.Verify());
}

// The fake the test uses. Its arithmetic is two lines.
private sealed class FlatFee(IPriceSchedule inner, Money fee) : IPriceSchedule
{
    public Money CentsFor(Grade grade, Volume volume) => inner.CentsFor(grade, volume) + fee;
    // The fee comes off the top, then the board decides how much fuel fits in what is left.
    public Volume MaxVolumeFor(Grade grade, Money money) => money <= fee ? Volume.Zero : inner.MaxVolumeFor(grade, money - fee);
    public string Display(Grade grade) => inner.Display(grade);
}

The third test in that group is the money one. The ceiling is a contract between the token and the valve. A wrapped schedule has to keep it. Three parts read the schedule through the interface:

  • the taper,
  • the creep floor,
  • the final cap.

So the sale still stops at or under $30, and the ledger still verifies.

4. The build, as a sketch

The injector is a delivery stage that takes the hose in slugs

// GasPump.Pump/AdditiveInjector.cs (sketch)
// Total and Slug in fl oz on the config surface; here already converted to Volume (16 oz = 125 mGal).
public sealed record AdditiveOptions(Volume Total, Volume Slug, TimeSpan Lead, Money Fee);

public sealed class AdditiveInjector(AdditiveOptions o, Volume reservoir, EventLedger ledger) : IDeliveryStage
{
    public string Name => "additive";
    public bool Selected { get; private set; }
    public bool Started { get; private set; }       // the fee is owed from here, whatever happens next
    public bool Empty { get; private set; }
    public Volume Reservoir { get; private set; } = reservoir;
    public Volume Delivered { get; private set; }
    private bool _holding;
    private Volume _inSlug;
    private string _saleId = "-";

    public void Select(bool on) => Selected = on;    // the handler refuses it after the first pour, like a grade

    public void OnArmed(string saleId)
    {
        _saleId = saleId; Selected = false; Started = false; Delivered = Volume.Zero; _holding = false; _inSlug = Volume.Zero;
    }

    // Fuel slug: count fuel until a slug's worth has passed, then take the hose again.
    public void OnDelivered(Grade grade, Volume delivered)
    {
        if (Started && !_holding && Delivered < o.Total) _inSlug += delivered;
    }

    public bool ClaimsHose(TimeSpan pouredFor)
    {
        if (!Selected || Empty || Delivered >= o.Total || pouredFor < o.Lead) return false;
        if (_holding) return true;
        if (!Started || _inSlug >= o.Slug) { _holding = true; _inSlug = Volume.Zero; Started = true; return true; }
        return false;
    }

    public Volume Pour(TimeSpan dt, FlowRate hoseFlow)
    {
        var moved = Volume.Min(hoseFlow.Over(dt), Volume.Min(o.Slug - _inSlug, o.Total - Delivered));
        if (moved > Reservoir) { Empty = true; moved = Reservoir; }
        Reservoir -= moved; _inSlug += moved; Delivered += moved;
        ledger.Append("additive.dose", $"{_saleId} {moved}, {Delivered} of {o.Total} delivered, reservoir {Reservoir}");
        if (_inSlug >= o.Slug || Delivered >= o.Total || Empty) { _holding = false; _inSlug = Volume.Zero; }
        return moved;
    }

    public IEnumerable<DiagnosticCode> Conditions() { if (Empty) yield return DiagnosticCodes.PumpAdditiveEmpty; }

    public bool TryRestoreCondition(string code)
    {
        if (code != DiagnosticCodes.PumpAdditiveEmpty.Code) return false;
        Empty = true;
        return true;
    }
}

Two parts write to the ledger:

  • The controller writes hose.switch on every flip.
  • The injector writes additive.dose on every slice it moves.

Both land in the ledger, so both are in the custody chain. The switching audit lives in the controller. The controller owns the valve, and a part shouldn't be the only witness to its own switching.

The fee is a price schedule that wraps the board

// GasPump.Pump/AdditivePricing.cs (sketch)
public sealed class AdditivePricing(IPriceSchedule board, AdditiveInjector injector, Money fee) : IPriceSchedule
{
    // The fee is owed in full from the first additive slug, whatever happens after: a fault
    // mid-slug still pays for the additive. Before the first slug nothing is owed, so a sale
    // that faults in the three-second lead, or never pours, carries no fee.
    private Money Fee(Volume v) => injector.Started ? fee : Money.Zero;

    public Money CentsFor(Grade grade, Volume volume) => board.CentsFor(grade, volume) + Fee(volume);

    // The fee comes off the top of the ceiling, then the board decides how much fuel fits in what is left.
    public Volume MaxVolumeFor(Grade grade, Money money) =>
        !injector.Selected ? board.MaxVolumeFor(grade, money)
        : money <= fee     ? Volume.Zero
        : board.MaxVolumeFor(grade, money - fee);

    public string Display(Grade grade) => board.Display(grade);

    // The receipt and the bank's settlement get two lines once the additive has started.
    public IReadOnlyList<ChargeLine> Lines(Grade grade, Volume volume) =>
        injector.Started
            ? [.. board.Lines(grade, volume), new ChargeLine("ADDITIVE", $"detergent additive {injector.Delivered}", fee)]
            : board.Lines(grade, volume);
}

The AIF (Assume It's Future) reading. A few dozen lines today open the door. The room, meaning the detergent, isn't built. The seam costs:

  • one interface,
  • one optional parameter,
  • three foreach loops.

Skipping it would have meant retrofitting later:

  • the money path,
  • the security path,
  • the restore table.

Each of those is a review of code nobody wants to reopen.

8. What still needs a registration, and why

Three edits land outside the new classes. Each is a one-line row in a table that's meant to take rows.

  1. The diagnostic code. DiagnosticCodes.All is a registry, and adding a row is how it grows. Four things read the row's ClearedBy and need no change:
    • the notice,
    • the refusal line,
    • the clear-when-fixed rule,
    • the docs table.
  2. The message. PumpMessage is a closed union on purpose. That means a fixed list of messages the pump accepts. The security article's strongest control is the message that doesn't exist. A pump that accepted any message a plug-in defined would lose that control. So a new message is a visible, reviewable row with its JSON registration beside it.
  3. The handler case. Dispenser.Handle is the one place a message meets a part. One case per message keeps it readable, and this case is a handful of lines.

The pump face gains a button and a field. That's the screen's job, and anyone who wants to see the reservoir should be able to.

Everything else on the section 5 list stays as it was at commit 708bac5. The detergent can be built in an afternoon on top of what's there, and the review would be two new files and four one-line rows.

9. How the money flow changes

StationDispenserThe bank never has to learn what detergent is. Think of a restaurant check: one total, two lines. The bank gets a total and two charge lines, FUEL and ADDITIVE. That is all it needs. The fee reuses three things that already exist:

  • it sits inside the ceiling the pump already has,
  • it rides in the one money number the pump already reports,
  • it settles in the one completion the station already sends.
