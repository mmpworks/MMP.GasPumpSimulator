The patterns inside a pay-at-pump dispenser

A fuel dispenser has to move money and fuel at the same time, over links that fail. Here are the patterns the simulator uses to keep the two in step, with the code behind each one and a picture of where it sits.

1. The map

Two processes talk over one TCP socket on the loopback.

  • The station owns the sale and the money. A bank simulator sits behind it.
  • The dispenser owns:
    • the valve,
    • the meter,
    • the limits.

Every box below is a worker. Each one handles a single message at a time. Think of a worker as a clerk with one in-tray.

2. Strategy: three ways to run a worker

BothPattern. Strategy. One interface, three interchangeable ways to do the same job. Think of three drivers who can all take you to the same address.

src/GasPump.Dispatch/IDispatchStrategy.cs · ThreadedDispatch.cs · ChannelDispatch.cs · AsyncProxyDispatch.cs

The pattern, in general.

Strategy is a family of ways to do one job, each behind the same interface, so the caller picks one at runtime and the rest of the code never knows which. It solves one problem: a decision that would otherwise be an if inside every method that needs it. Three roles:

  • the context, the code that needs the job done (here, Simulation);
  • the strategy interface, the one shape every way must fit (IDispatchStrategy);
  • the concrete strategies, one class per way (threads, channels, AsyncProxy).

The test for a good strategy seam: you can add a fourth way without opening the context.

Three designs can run the workers:

  1. one thread per worker,
  2. a Task and a Channel per worker,
  3. a hand-built state machine on MMP.AsyncProxy.

They differ in three ways:

  • how workers run,
  • how mailboxes block,
  • how time arrives.

Everything above the interface is the same code in all three. The test suite runs the whole sale under each strategy with a fake clock.

public interface IDispatchStrategy : IDisposable
{
    string Name { get; }
    bool PrefersBlockingIo { get; }

    IMailbox<T> CreateMailbox<T>(string name, int capacity);

    // Starts a worker that drains the mailbox through the handler until disposed.
    IWorkerHandle StartWorker<T>(string name, IMailbox<T> inbox, Action<T> handle);

    // A repeating clock that posts a message each period. Disposing stops it.
    IDisposable StartTicker<T>(string name, TimeSpan period, IMailbox<T> target, Func<T> make);

    // A one-shot clock that posts a message once.
    IDisposable StartTimer<T>(string name, TimeSpan due, IMailbox<T> target, Func<T> make);

    // True when every mailbox is empty and no handler is mid-message.
    bool IsIdle { get; }
}

3. Actors and mailboxes

BothPattern. Actor model. Each worker owns its state and reads one mailbox. Nothing shares memory.

src/GasPump.Dispatch/Dispenser.cs · Simulation.cs · Messages.cs

The pattern, in general.

An actor is a unit of code that owns its own state and talks to the world only through messages in its own mailbox. It handles one message at a time, so its state never needs a lock. Three rules make something an actor:

  • no shared memory: another actor can send it a message and nothing else;
  • one message at a time, in arrival order;
  • a bounded mailbox, so a flood makes the sender wait or drop instead of filling memory.

The payoff is that most thread problems (races, deadlocks, torn reads) cannot happen, because there is nothing two threads can touch at once.

Three rules hold for every strategy. They're written on the interface, so a new strategy can't forget them.

1. A worker handles one message at a time, on one logical thread. Handlers never run at the same time.

2. Timers never run code. They post a message. The worker runs the code.

3. Workers never share state. They pass messages.

The pump worker has one entry point. A message goes in. Zero or more sale events come out. The worker posts those events to the sale worker. The same method serves the in-process pump and the pump in another process.

// Runs on the pump worker only. The sale id is the station's current sale,
// which the pump needs only to address the events it sends back.
public IReadOnlyList<SaleEvent> Handle(PumpMessage m, string saleId)
{
    var events = new List<SaleEvent>(2);
    switch (m)
    {
        case PumpMessage.Arm arm:
            var (ok, reason, armed) = Pump.Arm(arm.SaleId, arm.Token, arm.Grade);
            if (ok) events.Add(new SaleEvent.PumpArmed(arm.SaleId, armed!.Ceiling, armed.MaxVolume));
            else    events.Add(new SaleEvent.PumpRefused(arm.SaleId, reason));
            break;

        case PumpMessage.Lift:
            if (Pump.LiftNozzle()) events.Add(new SaleEvent.NozzleLifted(saleId));
            break;
        // ... InsertSpout, Squeeze, Release, Hang, Tick, Stop, the forecourt faults
    }
    return events;
}

Mailboxes are bounded. A full mailbox makes the sender wait, like a full in-tray at a clerk's desk. A pulse stream can't drop a count. So the producer takes the delay and the consumer keeps every pulse. The code marks this as the house gem back-pressure-ring.

4. State machine that returns commands

StationPattern. Table-driven state machine plus Command. The machine decides. The caller acts.

src/GasPump.Core/SaleStateMachine.cs · Sale.cs · src/GasPump.Dispatch/Simulation.cs (Execute)

The pattern, in general.

A state machine is a fixed list of states and the events that move between them. A table-driven one keeps that list in one place (a switch over state and event) so every legal move is visible and every other move is refused by default. Command is the companion: the machine returns a list of small records that say what to do (ArmPump, SendCompletion) and someone else does it. Together they give you a core with no I/O, which means:

  • a test is a list of events in and a list of commands out;
  • the same core runs under any threading model, because it never touches a thread;
  • the illegal move is a logged no-op, never a crash.

The sale machine touches none of these:

  • a thread,
  • a timer,
  • a socket,
  • a valve.

Apply takes one event. It returns the commands the outside world should run. A list of records and a fake clock are enough to test the whole machine.

public IReadOnlyList<SaleCommand> Apply(SaleEvent e)
{
    if (e.SaleId != SaleId)
        return [new SaleCommand.Log(SaleId, $"dropped event for other sale {e.SaleId}")];

    var commands = new List<SaleCommand>(4);

    // Money events are legal in every state. They move Hold.
    if (ApplyHoldEvent(e, commands)) return ClearIfRepaired(commands);

    // Service reports are legal in every state.
    if (e is SaleEvent.PumpService ps) return ApplyService(ps, commands);

    switch (State, e)
    {
        case (SaleState.Idle, SaleEvent.CardPresented cp):
            CardName = cp.CardName;
            Tender = cp.Tender;
            Source = cp.Source;
            Hold = HoldStatus.Requested;
            commands.Add(new SaleCommand.RequestAuthorization(SaleId, cp.CardName, Grade, cp.Tender));
            return Transition(SaleState.Authorizing, commands, "card presented", timeout: _timeouts.Authorization);
        // ... one case per (state, event) pair
    }
}

The commands are plain records. The simulation reads them and does the side effects. The two money cases follow an order:

  1. Write to the compensation log, on the deciding thread.
  2. Post to the payment worker.

Section 6 covers why.

private void Execute(SaleCommand c)
{
    switch (c)
    {
        case SaleCommand.ArmPump ap:
            _link.Post(new PumpMessage.Arm(ap.SaleId, ap.Token, ap.Grade), ap.SaleId);
            break;
        case SaleCommand.CloseValve cv:
            _link.Post(new PumpMessage.Close(cv.SaleId, "sale closed"), cv.SaleId);
            break;
        case SaleCommand.SendCompletion sc:
            Gateway.Intend(new PendingAdvice(sc.SaleId, PendingKind.Completion, sc.Final));
            _paymentBox.Post(new PaymentMessage.Complete(sc.SaleId, sc.Final));
            break;
        case SaleCommand.Reverse rv:
            Gateway.Intend(new PendingAdvice(rv.SaleId, PendingKind.Reversal, Money.Zero));
            _paymentBox.Post(new PaymentMessage.Reverse(rv.SaleId));
            break;
        case SaleCommand.ArmTimer at:   /* start the one sale timer */ break;
        case SaleCommand.CancelTimer:   /* stop it */ break;
        case SaleCommand.Log lg:        Log.Write("sale", lg.Message); break;
    }
}

5. The sale as a saga, and what a saga is

StationPattern. Saga. Each step toward "fuel for money" has a step back. A hold is reversed. A completion is queued.

src/GasPump.Core/SaleStateMachine.cs (ApplyHoldEvent) · Sale.cs (HoldStatus)

The pattern, in general.

A saga is a long-running piece of business that has to cross more than one system, where you cannot lock everything in one database transaction. Instead of one big all-or-nothing step, you break it into a chain of small local steps. Each step commits on its own. Each step also has a compensating step: an action that undoes its effect if a later step fails. If step 3 fails, you run the undo for step 2, then the undo for step 1, and the business ends up where it started. That is the whole idea.

The parts of a saga:

  • Steps, each one a local change in one system. Ours: ask the bank for a hold, arm the pump, dispense fuel, settle with the bank.
  • Compensations, one per step, each written so running it twice is harmless. Ours: reverse the hold, disarm and close the valve, settle for the fuel that moved (fuel cannot come back), queue the settlement if the bank is unreachable.
  • A coordinator that knows which step comes next and which undo to run when something fails. Ours is SaleStateMachine: it holds the sale in one place and returns the forward or backward command for each event. This is the orchestration style. The other style, choreography, has each system react to the last one's event with no coordinator; it is harder to read and harder to recover.
  • A saga log, a record of how far the chain got, so a crash can resume or unwind. Ours is in three layers: HoldStatus says where the money is, the journal snapshots the sale every second, and the write-ahead compensation log records any undo or settlement before it is sent.
  • Recovery direction. Backward recovery unwinds: no fuel moved, so give the hold back. Forward recovery pushes through: fuel moved, so the only correct ending is to settle for it. The recovery table picks the direction from what the log says.

Why not one big transaction? The bank is another company on the far end of a network. You cannot hold a lock on their ledger while a driver pumps gas for three minutes. A saga accepts that the two sides will be out of step for a while, and makes every in-between state a named, visible one with a known way out. That is what the two columns in the sales book are: State is how far the pump got, Hold is how far the money got, and the gap between them is where the compensations live.

The machine tracks two things apart:

  • where the money is (Hold),
  • where the pump is (State).

The two drift apart when the bank link runs late. That gap is where every "I was charged and got no gas" story lives. Anyone who has stood at a pump wondering whether the card went through knows the feeling. So the driver gets told about the gap.

public enum HoldStatus
{
    None,            // No request has gone to the bank.
    Requested,       // A hold was requested and no answer has come back yet.
    Held,            // The bank holds the money. Fuel may flow.
    Settled,         // The hold was settled to the real amount. The sale is paid.
    Released,        // The hold was released in full. Nothing was charged.
    SettlePending,   // Fuel moved, the link was lost, the settlement sits in a queue.
    ReleasePending,  // No fuel moved, the link was lost, the release sits in a queue.
}

The nasty case is a late approval. The pump has already told the driver "no". An approval that shows up now gets reversed. It is never armed. Picture a receipt that prints after you left the store: the clerk voids it.

// The saga's compensation table. Returns true when the event was a money event.
private bool ApplyHoldEvent(SaleEvent e, List<SaleCommand> commands)
{
    switch (e)
    {
        case SaleEvent.Approved late when State != SaleState.Authorizing:
            // Late approval after we gave up. The bank holds money for a sale we already ended. Give it back.
            Hold = HoldStatus.Held;
            commands.Add(new SaleCommand.Reverse(SaleId));
            commands.Add(new SaleCommand.Log(SaleId, $"LATE approval {late.Ceiling} arrived in {State}; token discarded, hold reversed"));
            return true;

        case SaleEvent.ReversalQueued:
            Hold = HoldStatus.ReleasePending;
            commands.Add(new SaleCommand.Log(SaleId, "bank unreachable, release queued, will post when the link returns"));
            return true;

        case SaleEvent.CompletionQueued cq when State == SaleState.Completing:
            Hold = HoldStatus.SettlePending;
            Transition(SaleState.StoreAndForward, commands, $"host down, completion for {cq.Final} queued", timeout: _timeouts.Notice);
            return true;
        // ... Declined, Reversed, CompletionSent
    }
    return false;
}

6. Write-ahead compensation log

StationPattern. Write-ahead log, shaped like a transactional outbox. The intent reaches disk before the wire is tried.

src/GasPump.Payment/PaymentGateway.cs · src/GasPump.Dispatch/Simulation.cs

The pattern, in general.

A write-ahead log records what you are about to do before you do it, on a surface that survives a crash. The transactional outbox is the same idea for messages: write the outgoing message into your own store in the same step as the decision, and let a separate sender deliver it later. The order is the whole pattern:

  1. decide;
  2. write the intent to disk;
  3. only then try the wire;
  4. on restart, read the log and finish anything still open.

It trades one extra disk write per decision for the guarantee that a crash between "decided" and "sent" loses nothing.

A reversal or a completion is money the station owes the bank. The decision used to live only in a message between two threads until the bank answered. A crash in that window lost it. Now the order is:

  1. The gateway records the advice in its queue.
  2. The queue raises an event.
  3. The station writes the journal on that event.
  4. Only then does anything go on the wire.
// Record what the bank is owed before anything is sent. A second call for the same sale and kind changes nothing.
public void Intend(PendingAdvice advice)
{
    if (TenderOf(advice.SaleId) == Tender.Cash) return;   // cash settles at the till
    if (Enqueue(advice)) PendingChanged?.Invoke();
}

// In Simulation's constructor:
// The compensation log reaches disk the moment it changes.
Gateway.PendingChanged += () => SaveJournal();

There's one send path. The payment worker drains the queue:

  • oldest first,
  • removing an advice only after the bank has it,
  • stopping at a failure and keeping the rest.
public async Task<IReadOnlyList<PendingAdvice>> DrainPendingAsync(CancellationToken ct)
{
    var sent = new List<PendingAdvice>();
    while (true)
    {
        PendingAdvice next;
        lock (_gate)
        {
            if (_pending.Count == 0) return sent;
            next = _pending[0];
        }
        var result = next.Kind == PendingKind.Completion
            ? await _network.SendAsync(() => { _issuer.Complete(next.SaleId, next.Final); return true; }, _options.HostTimeout, ct)
            : await _network.SendAsync(() => { _issuer.Reverse(next.SaleId); return true; }, _options.HostTimeout, ct);
        if (!result.Delivered) return sent;
        lock (_gate) _pending.Remove(next);
        sent.Add(next);
        PendingChanged?.Invoke();
    }
}

// One advice per sale and kind. A retry that fails again must never double the queue.
private bool Enqueue(PendingAdvice advice)
{
    lock (_gate)
    {
        if (_pending.Any(p => p.SaleId == advice.SaleId && p.Kind == advice.Kind)) return false;
        _pending.Add(advice);
        return true;
    }
}

7. Idempotent receiver and tombstone

BothPattern. Idempotent receiver. The same message twice has the same effect as once. Plus a tombstone for the message that arrives before the one it undoes.

src/GasPump.Payment/Issuer.cs

The pattern, in general.

An idempotent receiver gives the same result whether a message arrives once or five times. Networks retry, so any receiver that charges, ships, or counts on each arrival will double-count. The usual tool is a key on the message (a sale id, a request id) and a record of keys already handled. A tombstone covers the reverse race: the "undo" arrives before the "do". The receiver records that the undo happened, so when the original finally shows up it is refused instead of applied to nothing.

Repeats from the drain above cost nothing. The bank side treats a second completion or reversal as the same one. Doing it twice changes nothing.

public void Complete(string saleId, Money final)
{
    lock (_gate)
    {
        if (!_holds.Remove(saleId, out var hold)) return;   // duplicate completion, idempotent
        var acct = _accounts[hold.Pan];
        var refund = hold.Amount - Money.Min(final, hold.Amount);
        acct.Available += refund;
    }
}

On a slow network a reversal can outrun its own authorization (the bank's yes). The issuer remembers the void, like a tombstone. The late authorization then lands as a decline. It never becomes an orphan hold.

// Sale ids that were reversed before any hold arrived.
private readonly HashSet<string> _voided = new();

public void Reverse(string saleId)
{
    lock (_gate)
    {
        if (!_holds.Remove(saleId, out var hold))
        {
            _voided.Add(saleId);   // nothing to release yet; remember the void
            return;
        }
        _accounts[hold.Pan].Available += hold.Amount;
    }
}

public IssuerDecision Authorize(string saleId, CardData card, Money hold, DateTimeOffset now)
{
    lock (_gate)
    {
        if (_voided.Contains(saleId))
            return IssuerDecision.Decline(DeclineReason.DoNotHonor, "sale already voided by the terminal");
        // ...
    }
}

8. Value objects in whole units

BothPattern. Value object. A small type that holds one measured thing in whole units:

  • Money is whole cents.
  • Volume is thousandths of a gallon.
  • There's no double anywhere in the money path.

src/GasPump.Core/Units.cs

The pattern, in general.

A value object is a small immutable type defined by its value, not its identity: two Money(350) are the same money. It gives a unit a type so the compiler catches a dollar added to a gallon, and it holds the number in whole units (cents, thousandths of a gallon) so arithmetic never loses a fraction and rounding happens in one named place.

// Money is whole cents in a long, never a double.
public readonly record struct Money(long Cents) : IComparable<Money>
{
    public static Money FromDollars(decimal dollars) => new((long)Math.Round(dollars * 100m, MidpointRounding.AwayFromZero));
    public static Money operator +(Money a, Money b) => new(a.Cents + b.Cents);
    public static Money Min(Money a, Money b) => a <= b ? a : b;
    public override string ToString() => $"${Cents / 100}.{Cents % 100:00}";
}

// Thousandths of a gallon. A pulser click is one of these.
public readonly record struct Volume(long MilliGallons) : IComparable<Volume>
{
    public static Volume FromGallons(decimal gallons) => new((long)Math.Round(gallons * 1000m, MidpointRounding.AwayFromZero));
    public decimal Gallons => MilliGallons / 1000m;
}

Price is tenths of a cent per gallon. The conversion rounds half up with integer math. The ceiling check and the display use the same code, so the two can't disagree by a cent.

public Money CentsFor(Grade grade, Volume volume)
{
    // cents = mGal * tenthCents / gal / 10 / 1000, rounded half up.
    long numerator = volume.MilliGallons * PriceOf(grade);
    return new Money((numerator + 5_000) / 10_000);
}

9. One port, two adapters

BothPattern. Ports and adapters. The station talks to a port, like a wall socket. Two plugs fit it:

  • a mailbox in the same process,
  • a socket to another process.

The station code above the port is the same for both.

src/GasPump.Dispatch/DispenserLink.cs · Messages.cs · Sale.cs

The pattern, in general.

Ports and adapters (also called hexagonal architecture) puts an interface, the port, between the core and anything outside it: a socket, a file, a clock, a bank. Each outside thing gets an adapter that fits the port. The core sees only ports, so it can be tested with a fake adapter and shipped with a real one, and a new outside thing is a new adapter, never a change to the core.

// The seam between the station and the pump.
public interface IDispenserLink : IDisposable
{
    bool Connected { get; }
    void Post(PumpMessage m, string saleId);
    void PowerOff();                               // the station cuts the dispenser's power

    event Action<SaleEvent>? Event;
    event Action<DispenserView>? ViewChanged;
    event Action<bool>? ConnectionChanged;
    event Action<LogLine>? RemoteLog;              // never raised in-process, where the log is shared
    event Action<LedgerEntry>? RemoteLedger;
    IDisposable SubscribeCustody(Action<string, string> onLine);
}

The same records serve as the contract between two mailboxes and between two processes. No translation step sits between them. The wire needs one extra thing: a type tag on the base record.

[JsonPolymorphic(TypeDiscriminatorPropertyName = "$m")]
[JsonDerivedType(typeof(Arm), nameof(Arm))]
[JsonDerivedType(typeof(Close), nameof(Close))]
[JsonDerivedType(typeof(Squeeze), nameof(Squeeze))]
// ... Lift, InsertSpout, WithdrawSpout, Release, Hang, Tick, Stop, the fault hooks
public abstract record PumpMessage
{
    public sealed record Arm(string SaleId, string Token, Grade? Grade) : PumpMessage;
    public sealed record Close(string SaleId, string Reason) : PumpMessage;
    public sealed record Squeeze : PumpMessage;
    // There is no SetCeiling message.
}

10. Journal and a pure recovery table

StationPattern. Memento for the state, then a pure decision function over it. The decision has no I/O, so the whole table is testable with records.

src/GasPump.Dispatch/Recovery.cs · JournalRecords.cs · StateJournal

The pattern, in general.

Memento is a snapshot of an object's state that can be stored and later used to rebuild it. Paired with a pure decision function (state in, decision out, no I/O), it gives a recovery path you can test with records: write the snapshot on a timer, read it on restart, and let the function say what to do about what it finds. The function never touches a file or a network, so every branch of the recovery table is a one-line test.

The station writes a snapshot every second and on every sale change. On restart:

  1. RecoveryPlan.Build reads the last snapshot and the clock.
  2. It says what to do.
  3. The simulation carries it out.

The record also admits what it can't know. Fuel may have moved for up to one snapshot period after the last write.

public static RecoveryOutcome Build(JournalSnapshot? snapshot, DateTimeOffset now, TimeSpan snapshotPeriod)
{
    if (snapshot is null)
        return new(RecoveryKind.CleanStart, "", null, /* ... */ "no journal found, first run");

    var s = snapshot.Sale;
    var state = Enum.Parse<SaleState>(s.State);
    var hold  = Enum.TryParse<HoldStatus>(s.Hold, out var h) ? h : HoldStatus.None;
    var flow  = new FlowRate(s.FlowMilliGallonsPerSecond);
    // An E-stop writes its own final snapshot on the way down, so nothing flowed after it. A crash writes none.
    var estop = snapshot.StopReason == "ESTOP";
    var unrecorded = estop ? Volume.Zero : flow.Over(snapshotPeriod);

    switch (state)
    {
        case SaleState.Fueling when volume > Volume.Zero:
            return new(RecoveryKind.ClosedOut, /* ... */ unrecorded,
                $"closed for {volume} at {money}; delivery likely under-recorded by up to {unrecorded}");
        case SaleState.Fueling:
        case SaleState.Authorizing:
        case SaleState.ReadyToPump:
            return new(RecoveryKind.Reversed, /* ... */ "no fuel delivered; hold reversed");
        case SaleState.Completing:
            return new(RecoveryKind.CompletionResent, /* ... */ "completion sent again");
        // The sale had ended but the bank still held the money: the compensation never left. Finish it.
        case SaleState.Faulted or SaleState.Cancelled or SaleState.Declined
             when hold is HoldStatus.Requested or HoldStatus.Held && volume > Volume.Zero:
            return new(RecoveryKind.CompletionResent, /* ... */ "completion sent");
        default:
            return new(RecoveryKind.CleanStart, /* ... */ "nothing to close");
    }
}

11. Observer with replay

DispenserPattern. Observer, with a twist: a late subscriber first receives everything that already happened, under the same lock, so it holds the whole chain from the first line.

src/GasPump.Dispatch/CustodyStream.cs · src/GasPump.Security/EventLedger.cs

The pattern, in general.

Observer lets any number of listeners subscribe to a source and be called when something happens, without the source knowing who they are. The weak spot is the late joiner: a listener that subscribes after some events have fired never sees them. Observer with replay fixes that by handing a new subscriber the history first, under the same lock that publishes new events, so no event can slip into the gap between "caught up" and "subscribed".

// Attach a subscriber and first hand it every complete line already in the file,
// from the header on. Done under the lock so no line lands between the replay
// and the subscription.
public void SubscribeWithReplay(Action<string> onLine)
{
    lock (_gate)
    {
        if (File.Exists(Path))
        {
            using var fs = new FileStream(Path, FileMode.Open, FileAccess.Read, FileShare.ReadWrite);
            using var reader = new StreamReader(fs, System.Text.Encoding.UTF8);
            var text = reader.ReadToEnd();
            var complete = text.LastIndexOf('\n');
            if (complete >= 0)
                foreach (var line in text[..complete].Split('\n')) onLine(line.TrimEnd('\r'));
            var replayedBytes = System.Text.Encoding.UTF8.GetByteCount(text[..(complete + 1)]);
            if (replayedBytes > _offset) { _offset = replayedBytes; _partial.Clear(); }
        }
        Line += onLine;
    }
}

The ledger uses the simple form. Every append raises one event. In that one handler, the dispenser server does two things:

  • forwards the entry over the wire,
  • saves its state.
public event Action<LedgerEntry>? Appended;

public LedgerEntry Append(string kind, string detail)
{
    LedgerEntry entry;
    lock (_gate)
    {
        var prev = _entries.Count == 0 ? Genesis : _entries[^1].Hash;
        var seq = _entries.Count + 1;
        var at = clock.GetUtcNow();
        entry = new LedgerEntry(seq, at, kind, detail, prev, LedgerEntry.Compute(seq, at, kind, detail, prev));
        _entries.Add(entry);
    }
    Appended?.Invoke(entry);   // outside the lock
    return entry;
}

12. Derive, don't store

DispenserPattern. Derived state and a value-equal status record. The pump's service status is read from the part sensors every time. Nothing is stored, so a fixed part can never still read as broken.

src/GasPump.Pump/PumpController.cs · src/GasPump.Core/Diagnostics.cs

The pattern, in general.

Derived state is a value you compute from the facts every time you need it, instead of storing a copy that has to be kept in sync. Stored copies drift: the sensor says fixed, the flag still says broken. If computing it is cheap, derive it. A value-equal record for the result (two statuses with the same parts compare equal) makes "did it change?" a plain comparison.

// The conditions holding this pump out of service, read from the part sensors now.
public ServiceStatus Service => ServiceStatus.Of(Conditions());

// One sensor per row. The order is fixed, so the first entry is the one an arm refusal names.
private IEnumerable<DiagnosticCode> Conditions()
{
    if (hydraulics.BreakawaySeparated) yield return DiagnosticCodes.PumpHoseBreakaway;
    if (!hydraulics.SupplyAvailable)   yield return DiagnosticCodes.PumpSupplyNoFlow;
    if (meter.PulserDead)              yield return DiagnosticCodes.PumpMeterNoPulse;
}

Two statuses with the same codes are equal. A view that carries one changes only when a part does. So the station emits one PumpService event per real change, and none for noise.

public sealed record ServiceStatus(IReadOnlyList<string> Codes)
{
    public static ServiceStatus Of(IEnumerable<DiagnosticCode> conditions) => new([.. conditions.Select(c => c.Code)]);
    public bool InService => Codes.Count == 0;
    public bool Equals(ServiceStatus? other) => other is not null && Codes.SequenceEqual(other.Codes);
}

Each diagnostic code carries what clears it. Two readers use the same table:

  • the driver's notice,
  • the ledger's refusal line.

So they can't say two different things.

{
    public bool OutOfService => ClearedBy != ServiceAction.NextArm;
    public string Format(string detail) => $"[{Code}] {detail}";

13. Decide at the authoritative boundary

DispenserPattern. Verify, then clamp, where the context lives. The pump has its own:

  • limits,
  • clock,
  • nonce history (the list of numbers already used once).

So the pump decides. The station proposes a ceiling and the pump gets the last word.

src/GasPump.Security/PumpAuthority.cs · HardLimits.cs

The pattern, in general.

Decide at the authoritative boundary means the component that owns a resource makes the final call about it, and treats every incoming value as a proposal to check, not an order to obey. Upstream can be wrong, late, or hostile. The owner verifies what it can (a signature, a time window, a one-time number) and then clamps the request to limits it holds itself. Trust ends where ownership ends.

public (ArmedAuthorization? Armed, string Refusal) TryArm(string saleId, string tokenWire)
{
    var now = clock.GetUtcNow();
    var (auth, failure) = verifier.Verify(tokenWire, now);
    if (auth is null) { ledger.Append("arm.refused", $"{saleId} {failure}"); return (null, failure.ToString()); }

    var ceiling   = Money.Min(auth.Ceiling, limits.MaxMoneyPerSale);
    var maxVolume = Volume.Min(auth.MaxVolume, limits.MaxVolumePerSale);
    var clamped   = ceiling != auth.Ceiling || maxVolume != auth.MaxVolume;

    ledger.Append("arm.ok", $"{saleId} ceiling {ceiling} max {maxVolume} {(clamped ? "clamped" : "within limits")}");
    return (new ArmedAuthorization(saleId, ceiling, maxVolume, duration, clamped, note), "");
}
