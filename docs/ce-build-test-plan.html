Build for Windows CE, test in VMware

We want to write programs for Windows CE on a normal PC, then test them on a copy of CE running inside VMware. This page lays out the plan and shows how far we've gotten.

Where we stand. The build works today, but nothing from this work has run on Windows CE yet.

What's next. Steve asks Microsoft for the activation key for Compact 7, the official name for CE 7, and everything after the build waits on that key.

The pipeline

The programs use the .NET Compact Framework 3.5 (CF 3.5), the small version of .NET made for CE. Our CE box will be a virtual machine (VM), which is a whole computer running as software on another computer.

  1. 1. BuildA PC makes the .exe, the DLLs, and the support files.
  2. 2. PrepareVMware puts the CE VM back to a clean snapshot and starts it.
  3. 3. CopyA script sends the files to the VM over FTP.
  4. 4. RunA script starts the test program, and the program writes a result file.
  5. 5. ReportA script picks up the result file and reports N of M passed.

Steps 4 and 5 are new since our first outline. Copying files over can't tell us if a test passed, so something has to run the test and bring the answer back.

Step 1: Build on the PC

Copy the project setup from MMP.AsyncProxy: src/MMP.AsyncProxy.NetCF/MMP.AsyncProxy.NetCF.csproj. It's a normal SDK project that points at the CF libraries by path, so you don't have to change the registry or any system folder.

  1. Keep the CF libraries at E:\dev\tools\netcf35-ref. They're Microsoft's files, so they stay out of the repo, and docs/netcf-port.md in MMP.AsyncProxy records where they came from.
  2. MMP.AsyncProxy sets LangVersion to 3. Use the same setting for code that ships to CE.
  3. CF 3.5 leaves out parts of the desktop API. tools/netcf-audit.ps1 in MMP.AsyncProxy lists them, and the compiler catches the rest.
  4. C# code builds as AnyCPU, so the same file should run on any chip, but a native DLL, written for one kind of chip, needs a build for each chip you support.

Here's what we read back from the throwaway .exe after the build:

IMAGE v2.0.50727
REF mscorlib 3.5.0.0 969db8053d3322ac
REF System.Core 3.5.0.0 969db8053d3322ac
REF System.Windows.Forms 3.5.0.0 969db8053d3322ac

The key token 969db8053d3322ac marks a library as CF. MMP.AsyncProxy checks for the same token in CompactFrameworkTests.

This proof has a limit, because the .exe used more project settings than the MMP.AsyncProxy project does and we haven't rebuilt it with the simpler setup yet. Stage 2 below takes care of that.

Rider and Visual Studio settings

  1. The pipeline builds with dotnet build by default. It worked on SDK 10.0.204 with no extra setup on the machine.
  2. Visual Studio 2022 MSBuild needed the Microsoft.NetCore.Component.SDK component, and it also needed BypassFrameworkInstallChecks set to true in the project. Without that setting, it asks for the full .NET 3.5 SP1 feature, which a CF build doesn't use.
  3. In Rider, you pick the MSBuild on the Toolset and Build settings page. Try SDK 10.0.204 first.
  4. Expect to copy files to CE by hand or by script. We found no Rider support for CF debugging or a CF forms designer.

Step 2: The CE box in VMware

You can't install CE the way you install desktop Windows. Instead, a Microsoft tool called Platform Builder makes a system file named NK.bin, and a small boot program starts that file. Docker won't help here, because a container borrows the kernel (the core of the OS) from its host and CE has its own kernel.

Steps

  1. Make a Windows 7 or Windows 10 VM for building. Install Visual Studio 2008 first, then SP1, then Compact 7.
  2. Create an OS design for the CEPC x86 target. Add SYSGEN_DOTNETV35, SYSGEN_FTPD, and SYSGEN_TELNETD.
  3. Turn off KITL (the debug link to the build PC) and kernel debugging, then build NK.bin.
  4. Put the boot program on the disk first, then copy NK.bin. Microsoft warns that the other order fails the boot check.
  5. Boot a second VM from that disk. Start with the e1000 network adapter, which needs a CE driver for that chip. Give the VM 512 MB of fixed memory, the amount the Hyper-V guide uses.
  6. After the first good boot, take a snapshot named clean, which saves the VM so you can go back to that moment.

Microsoft's disk steps make a VHD, and we haven't tested how to move one into VMware. Compact 7 keeps the system file on a FAT32 disk, so we could also set up a VMware disk directly from the build VM.

If CF 3.5 doesn't start from the image, NETCFv35.wce.x86.cab in the CF installer gives us a second way to add it, although we haven't tested this.

Steps 3 to 5: Copy, run, and report

This script is a sketch, and it hasn't run yet. <ce-vm> stands for the address of the VM.

# 2. Clean box
vmrun -T ws revertToSnapshot ce7.vmx clean
vmrun -T ws start ce7.vmx nogui

# 3. Copy
curl -T CfSpike.exe "ftp://<ce-vm>/Temp/"

# 4. Run, through a Telnet session
\Temp\CfSpike.exe

# 5. Report
curl "ftp://<ce-vm>/Temp/result.txt" -o result.txt
vmrun -T ws stop ce7.vmx
  1. The result file decides pass or fail, and a missing file counts as a failure. The script prints N of M, and M comes from the test list so that the program being tested can't change it.
  2. Plan on writing a small test runner of our own, since we haven't confirmed that any current test framework works on CF 3.5.
  3. Keep the VM on a private VMware network and use an FTP login, because Microsoft warns against anonymous uploads.
  4. If Telnet fails, the HKEY_LOCAL_MACHINE\Init registry key can start a runner at boot, but that runner has to call SignalStarted.

If a step fails

What goes wrongWhat we do next
Microsoft won't give us a keyStop the CE 7 VM path. That leaves a real CE device. Don't use a key or an image from an unofficial site.
Compact 7 won't boot on VMwareTry the Hyper-V path from the blog: a Generation 1 VM, a legacy network adapter, and a cloned Virtual PC target.
CE boots but has no networkCopy the files onto the disk while the VM is off, and start the runner at boot. Get the results back the same way.
The program fails on CE but passes on the desktop CLRThe VM exists to catch this. Write it up in docs/ce-budget.md. MMP.AsyncProxy runs its CF build on the desktop CLR (the desktop .NET runtime), and that tells us nothing about the CF runtime.

Risks we're living with for now

  1. Trials run out, since the Compact 7 tools last 180 days and Visual Studio 2008 lasts 90, and we don't know if a finished NK.bin keeps working after that. Check the license terms before stage 3, since the pipeline would keep using these tools.
  2. Microsoft support for CE 6 ended on 2018-04-10, so if we find a bug in CE, Microsoft won't fix it.
  3. Downloads can vanish, so keep local copies of the tools. The CF installer's US page returned 404 on 2026-11-04, while a direct Microsoft link still served the file.
  4. Newer compilers don't produce the same code as Visual Studio 2008, and a 2022 report says they build events with Interlocked.CompareExchange<T>, and that user's device sandbox rejected it. CF 3.5 has this method, but a locked-down device might still refuse it.

A note on the CF installer

The development PC now has two copies of NETCFSetupv35.msi, and their SHA-1 values differ. The MMP.AsyncProxy copy is 48eba5c9ae1856cda0c2b0833dfdc28c36dbbc04. The copy we downloaded from Microsoft on 2026-11-04 is f5227adeccc12a2a4a6ffb226c555987ef10b25f. We compared the two Debugger\BCL folders, and the files match byte for byte, so builds use the same libraries either way. The MMP.AsyncProxy page says Microsoft deleted the download, and that sentence needs an update.

What we recommend

Work through the stages in order, and stop after stage 1 to review, because that stage tests the biggest risks (the key, the VM, and CF on CE) before anyone spends time on pipeline scripts.
